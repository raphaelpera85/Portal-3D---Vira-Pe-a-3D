# Publicação

O projeto usa Next.js e está pronto para importação na Vercel a partir do repositório GitHub. O fluxo padrão da plataforma detecta Next.js e executa a instalação e o build.

`.env.local` é somente para desenvolvimento local e está ignorado pelo Git por conter segredos. Na publicação, cadastre os valores usados pelo portal em **Vercel → Project Settings → Environment Variables**, escolhendo os ambientes Preview e Production conforme o uso; salve e faça um novo deployment para aplicar alterações. O Git recebe apenas `.env.example`, com os nomes das variáveis e sem valores. A Vercel armazena esses valores fora do código-fonte.

| Variável | Origem e uso | Vercel |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | URL base do projeto, sem `/rest/v1/` | Sim |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Publishable key da Data API | Sim |
| `SUPABASE_SECRET_KEY` | `sb_secret_…`, operações privilegiadas no servidor | Sim, como segredo |
| `SUPABASE_SERVICE_ROLE_KEY` | Compatibilidade para chave legada | Sim, se esse projeto ainda a usa |
| `SUPABASE_DB_URL` | Conexão Postgres com senha, exclusiva da Supabase CLI | Não |

Nunca coloque chaves secretas ou a senha do banco em variáveis `NEXT_PUBLIC_*`, em commits ou em migrações. Se uma credencial for exposta, revogue-a no provedor e atualize os ambientes.

O Supabase aplica criptografia gerenciada em repouso no banco e exige HTTPS/TLS nas APIs do projeto. A aplicação também cifra os tokens OAuth do Mercado Pago e do Melhor Envio com AES-256-GCM; mantenha `MP_TOKEN_ENCRYPTION_KEY` e `ME_TOKEN_ENCRYPTION_KEY` distintas, server-only e com backup seguro. Os demais dados pessoais não recebem cifra adicional por coluna na aplicação: o acesso é controlado por autenticação, RLS e políticas do banco. Não use uma chave privilegiada para contornar essas políticas no navegador. Para reforçar autenticação, revise **Authentication → Settings → Password Security** e habilite a proteção contra senhas vazadas se o plano permitir; a documentação atual da Supabase informa que esse recurso exige Pro ou superior. Veja [segurança de senhas](https://supabase.com/docs/guides/auth/password-security), [proteção de dados](https://supabase.com/docs/guides/database/secure-data) e [TLS](https://supabase.com/docs/guides/security/tls).

Configure `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` e `NEXT_PUBLIC_SITE_URL` por ambiente antes de ativar o backend. Use a origem HTTPS pública em `NEXT_PUBLIC_SITE_URL`. Para verificar a propriedade de prefixo no Google Search Console, preencha `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION` com o token fornecido pelo Google; veja [docs/google-search-console.md](google-search-console.md). Não coloque chaves secretas em variáveis `NEXT_PUBLIC_*`.

Antes de habilitar recursos com persistência, confira `supabase migration list --db-url <SUPABASE_DB_URL>` e faça uma simulação com `supabase db push --dry-run --db-url <SUPABASE_DB_URL>`. O workflow **Supabase migrations** em GitHub Actions oferece essas mesmas operações: configure `SUPABASE_DB_URL` como secret do repositório e execute `dry-run` primeiro; escolha `apply` apenas depois de revisar a lista. O workflow aceita execução somente na branch `main` e não roda no deploy da Vercel. Não aplique arquivos SQL manualmente fora desse fluxo. `SUPABASE_DB_URL` é somente para a CLI, precisa apontar para o mesmo projeto indicado por `NEXT_PUBLIC_SUPABASE_URL` e permanece fora do Git e da Vercel. As migrações atuais incluem arquivos privados, solicitações, marketplace, pagamentos, notificações, contestações e o bucket privado temporário de evidências. Pagamentos só podem ser habilitados após conectar cada loja, configurar comissão e webhook, e validar o fluxo com contas de teste. Não configure comunicação como confirmação de pagamento.

Para notificações e manutenção, configure na Vercel `SUPABASE_SECRET_KEY` (ou a chave legada `SUPABASE_SERVICE_ROLE_KEY`), `CRON_SECRET`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL` e as variáveis `WHATSAPP_*` indicadas em [docs/integrations.md](integrations.md). O cron diário ao meio-dia UTC verifica até 24 fontes técnicas por execução durante o ciclo configurado em `CATALOG_SOURCE_CHECK_DAY_UTC` (segunda-feira por padrão), aceitando `0` a `6` (domingo a sábado), até concluir todas as fontes publicadas. `CATALOG_SOURCE_ALLOWED_HOSTS` pode acrescentar domínios oficiais aprovados, separados por vírgula. A verificação tenta primeiro `HEAD`, segue até três redirecionamentos apenas para hosts HTTPS permitidos e usa `ETag`/`Last-Modified` quando disponíveis. Sem esses validadores, baixa somente conteúdo HTML, XHTML, texto simples ou PDF de até 512 KiB para calcular SHA-256; até dois redirecionamentos adicionais permanecem limitados à lista de hosts permitidos. O monitoramento nunca altera automaticamente os dados do catálogo. Conteúdo acima do limite ou de tipo não aceito fica sem verificação automática. Cadastre e aprove os templates WhatsApp: o de loja com três parâmetros (`tipo e produto`, `quantidade`, `link do painel`) e, se quiser notificações de modelagem, o template separado `WHATSAPP_DESIGNER_TEMPLATE_NAME` com dois parâmetros (`título`, `link do painel do designer`). A aplicação despacha a fila em `after()` após registrar solicitações ou pedidos, sem bloquear a resposta; o cron também serve como varredura de recuperação para itens pendentes.

A mesma rotina diária remove até 100 uploads de entrega de modelagem e envios de modelos 3D abandonados há mais de 26 horas dos buckets privados. O processamento não exige um cron adicional e preserva os registros de staging caso o Storage não confirme a remoção.

Para pagamentos, configure as variáveis `MP_*` descritas em [docs/integrations.md](integrations.md), aplique todas as migrações existentes e cadastre o webhook `/api/payments/mercado-pago/webhook` no Mercado Pago com os eventos de orders e contestações. Não habilite vendas reais antes de validar o split, Pix/cartão, cancelamentos, reembolsos, webhook, estoque reservado e download pós-pagamento com contas de teste. Pedidos do carrinho e impressões personalizadas podem usar tarifas Melhor Envio, além da cotação manual; para emitir etiqueta, o vendedor informa a chave NF-e, revisa o custo e confirma o débito da própria carteira. O rastreio é sincronizado pelo webhook do provedor. Valide a emissão de etiquetas e o endpoint `/api/shipping/melhor-envio/webhook` em sandbox antes da operação real.

Para OCR, configure `GOOGLE_CLOUD_VISION_API_KEY` somente se habilitar a Cloud Vision API no Google Cloud Console e restringir a chave à API Vision. Essa chave é diferente do token `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION` do Search Console.

Administradores autenticados podem abrir `/admin/integracoes` para conferir a presença e o formato básico das variáveis no ambiente que respondeu à página. A tela nunca revela seus valores e não substitui uma chamada real de validação aos provedores; depois de alterar variáveis na Vercel, gere um novo deployment e confira a Production.

Para vincular vendedores ao Mercado Pago, crie uma aplicação configurada como marketplace Split 1:1 e Checkout Pro. Cadastre como Redirect URL exatamente `https://SEU-DOMINIO/api/payments/mercado-pago/callback` (com o domínio de `NEXT_PUBLIC_SITE_URL`) e cadastre `/api/payments/mercado-pago/webhook` para o evento de orders. Configure `MP_CLIENT_ID`, `MP_CLIENT_SECRET`, `MP_TOKEN_ENCRYPTION_KEY`, `MP_WEBHOOK_SECRET` e `MP_MARKETPLACE_FEE_PERCENT` como segredos server-only. Gere a chave de criptografia com `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`; mantenha-a estável e faça backup seguro, pois tokens salvos deixam de ser recuperáveis se ela for perdida. A aplicação usa OAuth com PKCE e renova tokens no servidor. O split 1:1 exige contas de vendedor Mercado Pago verificadas no nível KYC 6 e autorização OAuth de cada vendedor. Valide a integração, política de frete e reembolso com contas sandbox antes de ativar cobranças reais.

O projeto `virapeca3d` está conectado ao GitHub e recebe deploys de preview por branch; `main` é o branch de produção associado a `virapeca3d.vercel.app`. A configuração usa o cron diário `0 12 * * *`, compatível com o plano Hobby. O `ignoreCommand` curto do `vercel.json` chama `scripts/vercel-ignore-build.mjs`: mudanças em código, arquivos públicos/modelos, scripts de build, dependências e configurações continuam acionando builds; mudanças apenas em documentação, migrations, Space TripoSR, testes ou fixtures são ignoradas. O script usa `VERCEL_GIT_PREVIOUS_SHA` quando disponível e recorre a `HEAD^` no primeiro deploy da branch; se não conseguir ler o diff, permite a build. O deployment de produção é iniciado por push a `main`; confirme o estado `READY` na Vercel e verifique o domínio público após cada publicação. Alterações de esquema também exigem aplicar e conferir as migrações no projeto Supabase correto.

No plano Hobby, a Vercel publica o limite de 32 deployments em uma janela de 3.600 segundos e 100 em 86.400 segundos. Se o check do commit falhar com `build-rate-limit`, aguarde a janela correspondente antes do próximo push planejado; não crie commits vazios nem inicie um deploy manual para contornar o limite. Consulte os [limites atuais da Vercel](https://vercel.com/docs/limits), pois eles podem mudar.

## Arquivos 3D no Git e entrega para celulares

Medição operacional de 16/11/2026: o repositório contém 119 arquivos em `models/` (1,63 GB; pack Git 1,50 GiB). Os arquivos ficam fora de `public/` e o site os entrega por `raw.githubusercontent.com`; assim, não são copiados para o bundle estático da Vercel, que nesta revisão tinha 14,2 MB. O maior arquivo individual é um ZIP de 55,9 MB. O endpoint Raw respondeu HTTP 200, `Accept-Ranges: bytes`, CORS `*` e `Cache-Control: max-age=300` nos HEAD requests de Batman 3MF e do ZIP texturizado. O Git continua sendo a origem escolhida para evitar a cota gratuita de Storage, mas o volume aumenta o tempo de clone/build e os downloads grandes podem demorar em redes móveis; avalie armazenamento/CDN dedicado antes de ampliar muito o catálogo. A medição não testou retomada de download no navegador nem carregamento em conexão móvel lenta.
